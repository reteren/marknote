# Аудит границы WebView2 ↔ Rust

Дата аудита: 2026-09-14. Проверка статическая: прочитаны IPC-команды,
маршрутизация окон, атомарная запись, адаптеры форматов, live preview,
`tauri.conf.json` и capability. Приложение не запускалось, файлы вне проекта
не читались и не изменялись.

## Итог

В текущей модели MarkNote фронтенд и так должен уметь открыть выбранный
пользователем файл в любом месте диска, поэтому глобальная проверка
«путь только под каталогом приложения» была бы неправильной. Но это не
оправдывает отсутствие границы у картинок: документ извне может заставить
`read_image` прочитать любой доступный процессу файл, а затем передать его
байты в WebView. Сейчас это ограничено локальным процессом и визуальным
предпросмотром (повышения прав или сетевой отправки в коде не найдено), но
это реальная конфиденциальная поверхность и заодно неограниченный источник
потребления памяти.

Основные находки:

1. **Средняя серьёзность:** `read_image` принимает абсолютный путь и `..`,
   не проверяет принадлежность каталогу документа и не ограничивает размер.
2. **Средняя серьёзность для целостности данных:** сохранение не проверяет,
   не изменился ли файл на диске после открытия; гонка с другой программой
   может молча перезаписать её правки. Обычные ошибки атомарной записи старый
   файл не удаляют, но долговечность после отключения питания не гарантирована.
3. **Средняя серьёзность/совместимость:** `canonical_path` снимает с
   Windows-пути префикс `\\?\`; это ломает длинные пути, а для UNC может
   превратить `\\?\UNC\server\share\x` в некорректное `UNC\server\share\x`.
4. **Средняя серьёзность:** Ctrl+клик по ссылке блокирует только
   `javascript:`, но разрешает `data:`, `file:`, `vbscript:` и другие схемы
   передавать в `window.open`.
5. **Низкая/средняя серьёзность:** KaTeX получает пользовательскую формулу
   без ограничения `maxSize`; огромные размеры в `\\rule`/родственных
   конструкциях могут подвесить раскладку WebView.
6. **Средняя серьёзность для целостности:** неизвестное расширение считается
   Plain Text, поэтому двоичный файл не отклоняется, хотя SPEC обещает отказ
   для бинарных файлов. Двойной клик по такому файлу и последующее сохранение
   могут испортить его.

## 1. Команды, принимающие путь

В таблице «принимает» означает фактическое поведение исходника, а не только
ожидаемый путь из интерфейса. `..` не является уязвимостью для команд
открытия/сохранения само по себе: пользовательский редактор по смыслу
работает с произвольными файлами. Для `read_image` действует отдельное
ограничение SPEC: ссылка относительна документа, а `file://` вне каталога
документа запрещён.

### 1.1. Канонизация и граница произвольных файлов

`open_file` и `route_file` используют `windows::canonical_path`, но
`save_file` и `read_image` — нет. `canonical_path` вызывает
`std::fs::canonicalize`, а затем безусловно удаляет начало `\\?\`. На
Windows canonicalize обычно возвращает именно extended path для поддержки
длинных имён. Для локального `\\?\C:\...` это может работать, пока длина
помещается обратно в старый лимит; для `\\?\UNC\server\share\...` удаление
префикса оставляет `UNC\server\share\...` без начальных обратных слэшей.
Это наблюдаемый дефект совместимости, а не обход разрешений.

В редакторе не следует вводить общий запрет traversal/UNC/симлинков для
`open_file` и сохранения: это сломало бы легитимное открытие файла из любой
папки и сетевого ресурса. Нужны отдельные правила для IPC, которые возникают
из документа (прежде всего `read_image`), и корректная работа с extended path.

### 1.2. Бинарные файлы

`initialize` и `handle_single_instance` принимают каждый аргумент, для
которого `Path::is_file()` вернул true. `open_file` для неизвестного
расширения выбирает `PlainAdapter`, а его `decode` декодирует любые байты
через общий детектор кодировки; проверки бинарного содержимого нет. Поэтому
заявленное в `SPEC.md` «двоичные файлы не открываются» не выполняется. Это
не удалённое выполнение, но опасный сценарий порчи файла: пользователь
двойным кликом открыл бинарник, увидел мусор и нажал Save.

## 2. `read_image`: чтение постороннего файла

Реализация в `src-tauri/src/commands.rs:271-290`:

1. `data:`, `http://` и `https://` возвращаются без чтения.
2. Любой абсолютный `src` используется как есть.
3. Иначе `src` соединяется с `parent(docPath)`, без `canonicalize`, проверки
   `candidate` под каталогом документа или запрета symlink/junction.
4. `fs::read` загружает весь файл; затем создаётся Base64-строка примерно
   на 4/3 размера входа и ещё один ответ IPC.

Концептуальный сценарий (не выполнялся): документ содержит
`![](../../../../Windows/System32/config/SAM)` или абсолютный путь к любому
читаемому файлу. Resolver передаёт его в Rust, `fs::read` возвращает байты,
а команда помещает их в data-URL для WebView даже если браузер не сможет
нарисовать MIME `application/octet-stream`. Для текущего приложения это не
повышает права: процесс и так читает файлы от имени текущего пользователя,
и пути не уходят по сети автоматически. Но это всё равно нарушает обещание
«изображение относительно документа», раскрывает секретные байты внутри
процесса и станет существенно опаснее при добавлении экспорта/отправки.

Размер файла никак не ограничен. Ссылка на большой файл может занять память
в `fs::read`, Base64, IPC и WebView и привести к заметному зависанию или OOM;
ограничение предпросмотра документа в 5 МБ это не исправляет, потому что
картинка читается отдельным IPC после открытия маленького Markdown.

**Оценка: средняя конфиденциальность и средняя доступность.** До релиза
нужны canonicalize кандидата, явная политика (например, только внутри
каталога документа; внешние изображения — отдельное подтверждение), reject
устройств/NUL и лимит байтов до чтения. При этом глобальное ограничение
`open_file` на каталог документа вводить не следует.

## 3. Запись и сохранность исходного файла

`atomic_write::write_atomic` создаёт новый файл рядом с целью через
`create_new`, пишет `write_all`, вызывает `sync_all`, а затем заменяет цель
одной операцией. На обычном пути ошибки записи, нехватки места, readonly или
блокировки цель не удаляется заранее; временный файл удаляется в обработчике
ошибки (если сам процесс не погиб). Это хорошая базовая защита от сценария
«сначала удалить старый файл, потом не дописать новый».

| Сценарий | Что происходит | Вердикт |
| --- | --- | --- |
| Место закончилось во время записи временного файла или `sync_all` | Ошибка возвращается, целевой файл не трогается; временный файл пытаются удалить. | **Оригинал обычно сохранён.** Нужен тест заполненного диска/ошибки, сейчас гарантии после аварии нет. |
| Цель занята другой программой | `MoveFileExW` может вернуть sharing/access error; старый путь не удаляется предварительно. | **Потеря исходника при обычной ошибке не видна; UI должен оставить документ dirty и показать ошибку.** |
| Атрибут readonly | `save_file` проверяет `metadata.permissions().readonly()` до кодирования. `save_as` не делает такой проверки цели и полагается на результат `MoveFileExW`; поведение зависит от атрибута/ACL и гонки. | **Политика readonly не единообразна; явно отказать до замены.** |
| Цель — симлинк | `metadata` следует ссылке, а замена записи через Win32 не задаёт no-follow-политику; типичная замена может заменить саму запись ссылки, а не файл, на который она указывает. | **Не определено контрактом и опасно для целостности/ожиданий пользователя; выбрать явную политику.** |
| Родитель — symlink/junction | Временный файл создаётся в `path.parent()`, поэтому ОС может разрешить родителя в другой каталог; это особенно важно для пути из `save_as` или гонки. | **Для произвольного пользовательского пути допустимо, но нет проверки идентичности цели.** |
| Другая программа изменила файл после открытия | Перед `atomic_write` нет сравнения mtime/размера/хэша/идентификатора файла с моментом открытия. Текущий буфер всё равно заменяет путь. | **Настоящая потеря чужих правок, средняя/высокая серьёзность целостности.** Watcher может уведомить о внешнем изменении, но не закрывает окно гонки между проверкой события и записью. |
| Сбой питания после `sync_all`, но до/во время replace | Временный файл синхронизирован, но Windows-вызов использует только `MOVEFILE_REPLACE_EXISTING`, без `MOVEFILE_WRITE_THROUGH`; отдельной синхронизации каталога нет. | **Логическая атомарность есть, durable commit не гарантирован.** После аварии нельзя обещать строго старую или новую версию. |

До релиза приоритетны проверка внешнего изменения перед записью и явная
обработка конфликта, затем no-follow/realpath-политика для симлинков и
durable replace (`WRITE_THROUGH`/эквивалент и проверка на целевой Windows).

## 4. CSP, capabilities и ассоциации

### CSP (`src-tauri/tauri.conf.json:29`)

```
default-src 'self';
img-src 'self' data: https: asset: http://asset.localhost;
style-src 'self' 'unsafe-inline';
font-src 'self' data:
```

- `default-src 'self'` без отдельного `script-src` означает запрет внешних
  скриптов по fallback; по исходнику удалённой загрузки скрипта не найдено.
- `img-src data:` обоснован data-URL, который возвращает Rust для локальных
  картинок. `https:` обоснован требованием SPEC разрешать удалённые HTTPS-
  изображения. `http://` в CSP отсутствует, хотя SPEC говорит, что HTTP-
  изображения загружаются: это функциональное расхождение в более строгую
  сторону, а не расширение атаки.
- `asset:` и `http://asset.localhost` в исходнике приложения не используются
  (нет `convertFileSrc`/asset URL и нет frontend-вызовов plugin-fs). Возможно,
  они оставлены для стандартного Tauri asset protocol; это надо подтвердить
  перед удалением. Само наличие в CSP не даёт shell-доступа, но расширяет
  допустимые источники без доказанной необходимости.
- `style-src 'unsafe-inline'` практически объясним: Svelte, CodeMirror
  StyleModule и лениво загружаемый KaTeX добавляют style в DOM. Это ослабляет
  последствия будущего XSS, но текущий документ не вставляет HTML. Если
  сборка позволяет, перейти на nonce/hash; иначе зафиксировать, что это
  осознанное исключение.
- `font-src data:` по текущему KaTeX CSS не требуется (шрифты подключаются
  относительными URL), но его влияние ограничено шрифтами и имеет низкий
  приоритет.

### Capabilities (`src-tauri/capabilities/default.json`)

Окнам `main` и `win-*` выданы `core:default`, `dialog:default` и `fs:default`.
В frontend нет импорта `@tauri-apps/plugin-fs`: все файловые операции идут
через собственные Rust-команды и `std::fs`; `fs:default` фактически даёт
рекурсивное чтение application-specific каталогов с `deny-default`, а не
доступ к произвольному диску. Это не причина `read_image`, но разрешение и
сам `tauri-plugin-fs` выглядят неиспользуемыми и увеличивают поверхность при
будущем XSS. `dialog:default` разрешает все типы native dialog; frontend
напрямую их не вызывает, Rust использует native API плагина. После проверки
Tauri runtime их стоит удалить/сузить; `core:default` нужен для используемых
оконных событий, IPC и window API.

### Ассоциации файлов

`tauri.conf.json:41+` регистрирует не только Markdown, но также txt, JSON,
YAML, TOML, XML, CSS, JS, TS, Rust и Python. `FORMATS.md` прямо обещает:
после установки двойным кликом перехватывается только класс A (Markdown),
остальные форматы доступны через «Открыть с помощью». Это не IPC-уязвимость,
но реальное расхождение поставки и повышенный риск случайного открытия и
последующей порчи чужого текстового/исходного файла. Дополнительно список
конфига не содержит заявленный в FORMATS `.mdx`. Исправить список ассоциаций
до релиза.

## 5. Документ как недоверенный источник данных

Прямой HTML-инъекции через Markdown в просмотренном коде не найдено:

- обычный текст, заголовок callout, подпись изображения, сноска и fallback
  картинки устанавливаются через `textContent` или DOM-свойства;
- ссылка в live preview — `Decoration.mark`, а не созданный из текста
  `<a href>`, URL не попадает в HTML-атрибут;
- иконки callout используют `innerHTML`, но SVG возвращается только из
  фиксированного switch по allowlist из девяти типов, пользовательский title
  вставляется отдельно через `textContent`;
- `<script>`/HTML из исходного Markdown не имеют renderer, который бы
  вставлял их в DOM; в CodeMirror это остаётся текстом;
- `ImageWidget` задаёт `img.src`, `alt` и `aria-label` как свойства/атрибуты,
  не конкатенирует HTML. Data/HTTP(S) URL из документа действительно
  загружается как изображение по предусмотренному контракту.

### Ссылки

`plugin.ts:211-220` на Ctrl+клик извлекает URL и отбрасывает только
`/^javascript:/i`, после чего вызывает `window.open`. Сценарий проверки:
ссылка `[x](data:text/html,... )` или `[x](file:///...)` проходит этот тест и
передаётся в новый контекст; `vbscript:` и custom schemes также не запрещены.
Статически нельзя утверждать, откроет ли конкретная версия Tauri/WebView2
такой URL во встроенном окне или во внешнем обработчике, но allowlist схем
отсутствует. При встроенном новом окне `data:text/html` может стать активным
содержимым вне ожидаемого Markdown-контекста; при внешнем обработчике это
как минимум нежелательный запуск. `javascript:` с точным началом блокируется,
но blacklist ненадёжен.

**Оценка: средняя.** Разрешать только `https:`/`http:` (если это требуется
спецификацией), направлять их через контролируемый внешний opener и отдельно
решить, нужны ли `mailto:` и другие схемы. Для `file:`/`data:`/`javascript:`/
`vbscript:` нужна безусловная блокировка.

### KaTeX

`MathWidget` вызывает `katex.renderToString` с `throwOnError: false` и
`output: "htmlAndMathml"`, а результат помещается в `innerHTML`. В установленном
KaTeX 0.18.7 параметр `trust` по умолчанию `false`, и код не включает
доверенный режим: HTML-команды/URL, требующие trust, не становятся
доверенными. Невалидная формула превращается в визуальную ошибку, а не
исключение; `maxExpand` KaTeX по умолчанию ограничивает макрорасширение.

Остаётся DoS-поверхность: `maxSize` в вызове не задан, а default KaTeX —
бесконечность. Враждебная формула вроде `\\rule{500000em}{500000em}` может
создать экстремальный размер элемента и затормозить layout/scroll WebView.
**Оценка: низкая/средняя доступность.** Зафиксировать `trust: false` явно и
задать разумный `maxSize` (а также оставить ограничение исходного документа
и кэш).

## 6. Аргументы запуска и ассоциации

`windows.rs:177-220` обрабатывает `env::args().skip(1)` на первом запуске и
`argv.into_iter().skip(1)` в single-instance callback. Каждый аргумент,
для которого `Path::is_file()` истинен, передаётся в `route_file`; остальные
просто игнорируются.

- Аргумент, похожий на ключ (`--foo`), не разбирается как опция. Если в
  текущем каталоге действительно есть файл с таким именем, он будет открыт;
  иначе проигнорирован. Внешней команды через shell нет.
- Несколько файлов открываются все: первый занимает пустое `main`, следующие
  маршрутизируются в другие окна. Ограничения числа аргументов/окон нет; очень
  длинный список может потребить ресурсы и создать много окон (низкая
  доступность, локальный вызывающий уже имеет возможность запустить процесс).
- Каталог, включая каталог через junction, `is_file()` не проходит и
  игнорируется. Симлинк/junction на обычный файл проходит `is_file()`, после
  чего `route_file` канонизирует конечный файл. Это ожидаемо для открытия
  произвольного пользовательского файла.
- Относительные аргументы разрешаются относительно текущего каталога
  процесса. UNC/длинные пути доходят до того же проблемного
  `canonical_path`, описанного выше.
- Устройство, несуществующий путь и NUL-байт обычно дают false/ошибку ОС;
  Rust `Command` для Explorer не используется в этом месте. Ввод не
  интерпретируется shell-ом.

Таким образом, разбор аргументов не даёт очевидной command injection. Нужны
исправление canonicalization и лимит количества окон как hardening, а не
запрет произвольных путей.

## Что сделать до релиза (по важности)

1. **Сохранение:** сравнивать состояние файла на диске с состоянием при
   открытии перед `save_file`; при конфликте не заменять файл молча, а показать
   выбор пользователя. Зафиксировать поведение symlink/junction и проверить
   durable replace на Windows, включая сбой/нехватку места.
2. **Картинки:** canonicalize `docPath` и кандидат, запретить выход из
   разрешённого каталога (или требовать отдельное подтверждение), ограничить
   размер до `fs::read`, отклонять устройства и NUL.
3. **Ссылки:** заменить blacklist на allowlist безопасных схем и не открывать
   `data:`/`file:`/`javascript:`/`vbscript:` в контексте приложения.
4. **Пути Windows:** не снимать `\\?\` безусловно; сохранить extended/UNC
   форму или корректно преобразовать только локальный путь, добавить тесты
   для UNC и >MAX_PATH.
5. **Форматы:** добавить проверку бинарности до `open_file` и отказывать
   согласно SPEC; убрать из установщика ассоциации классов B/C/D, оставив
   Markdown-класс A (и синхронизировать `.mdx`).
6. **KaTeX:** явно передать `trust: false` и ограничить `maxSize`; оставить
   `throwOnError: false`.
7. **CSP/capability:** подтвердить необходимость `asset:`/`http://asset.localhost`,
   `font-src data:` и `fs:default`; удалить неиспользуемые fs/dialog plugin
   permissions либо сузить их. `unsafe-inline` оставить только с
   документированным обоснованием или заменить nonce/hash, если это не ломает
   CodeMirror/Svelte.
